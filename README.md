- **張掌→長握拳**：YouTube 中持續握拳達 0.5 秒／0.7 秒／1 秒（沿用設定頁的可選時間），改為一次 `AudioManager.dispatchMediaKeyEvent(KEYCODE_MEDIA_PLAY_PAUSE)`，不會先送中央點擊，也不會再送第二次中央點擊；同一次長握拳不得重複發送媒體指令。
- **其他 App**：保留 v0.2.7 的普通握拳中央點擊與長握拳第二次點擊邏輯，張掌滑動、右滑返回、食指懸浮游標與其 1／2／3 秒停穩點擊仍保持不變。
- Android 媒體播放／暫停指令由目前接收媒體鍵的 App 決定實際效果；即使 YouTube 正在前景，仍可能因為媒體焦點、播放模式、系統或 YouTube 版本差異而無效。**不能宣稱已經在實機驗證 YouTube 能暫停**。
- 解鎖時仍需要正常三星臉部驗證；延用 v0.2.7 已整合的獨立短暫 Activity 工作、熄屏間歇省電及 10 分鐘上限。無相機上傳或網路權限。
- 安裝：`tw.airgesture.controller`、`versionCode=10`、使用原本的 Android 固定簽章，直接覆蓋 v0.2.7。
- 實測：開啟 YouTube 影片，先試短握拳是否正常單擊，再試長握拳是否切換播放／暫停；如無反應，查看設定頁中的本機診斷紀錄是否有「YouTube 長握拳：已發送媒體播放／暫停鍵」，以區分手勢未成立與媒體鍵未被 YouTube 接收。

# AirGestureController v0.2.6 — 解鎖後保留原本影片畫面

**修正 v0.2.5 已回報問題**：用「張掌→三星臉部解鎖」成功後，被帶回「隔空手勢控制器」設定頁，而不是原本看的影片。

- 原因：解鎖暫時 Activity 用 `FLAG_ACTIVITY_NEW_TASK` 時，會重用控制器自己的既有 task，暫時 Activity 結束就露出控制器 `MainActivity`。
- 修正：給 `FaceUnlockWakeActivity` 獨立的 `taskAffinity`；用 `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_MULTIPLE_TASK | FLAG_ACTIVITY_EXCLUDE_FROM_RECENTS` 建立不列入最近使用程式的短暫 task。
- Android 解鎖完成或 2.4 秒逾時後，若臉部驗證 Activity 是 task root，就呼叫 `finishAndRemoveTask()` 清除**僅該暫時 task**；不關掉原本的影片或控制器 service。若 ROM 非預期重用其他 task，則只關閉該 Activity，避免誤清空。
- 避免 `onResume` 多次對 Samsung `requestDismissKeyguard` 重複請求。
- 延用 v0.2.5 的全域隔空操作、獨立開關、預設熄屏間歇省電（3 秒開／5 秒關）、10 分鐘上限和固定簽章。
- 真機驗收：啟動 AirGestureController 並切回 YouTube/原影片 App，關閉螢幕→張掌→三星臉部驗證→解鎖後應回到**原影片 App**（而非 AirGestureController）；待 2～3 秒確認張掌上下滑或食指游標仍可使用。
- Android/OEM 仍控制背景 Activity 啟動、工作切換與臉部驗證，**尚需 S26 Ultra 實測**；若仍跳設定頁請回傳熄屏喚醒診斷紀錄以檢查 `taskId` / `isTaskRoot`。

# AirGestureController v0.2.5 — 熄屏張掌喚醒 + 省電模式

與 v0.2.4 同一套件 `tw.airgesture.controller`、同一固定簽章，可直接覆蓋。保留所有已測試正常的張掌上下滑、右滑返回、握拳中央點擊、食指游標停穩 3 秒點擊、斜角手掌輔助及快速揮掌設定。

## 新功能：熄屏喚醒後繼續操作
- App 內可啟用「螢幕關閉時張掌喚醒」（**預設關閉**）。
- 熄屏期間偵測到張掌約 1 秒，關閉相機，等待 CameraX 確認 CLOSED，額外交接 400ms，透過已在 Samsung S26 Ultra WakeProbe v0.1.2 實驗中成功的 `FaceUnlockWakeActivity.setTurnScreenOn` 和 `KeyguardManager.requestDismissKeyguard` 請求 Android 的**正常安全驗證**。
- 照常由三星臉部辨識完成解鎖，不繞過鎖定畫面。先在三星設定關閉「留在鎖定畫面直到滑動」。
- 完成解鎖約 1.8 秒後，重新取得同一套 CameraX + MediaPipe 辨識器，**自動恢復 v0.2.4 原本所有隔空手勢**，不再需要啟動 WakeProbe 或手動切換到另一 App。

## 熄屏省電
- 未啟用熄屏喚醒：**熄屏立即關閉前鏡頭**。
- 預設省電模式：**前鏡頭開約 3 秒／關閉約 5 秒**輪流掃描。手部剛出現時允許延長觀察，避免張掌還沒保持滿 1 秒就關鏡頭。
- 可改選「連續偵測」作為對照；辨識較及時，但鏡頭耗電較高。
- 相機開啟期間沒有手部時，AI 約每 440ms 取樣一次；發現手後約 140ms 一次。這只降低 AI 運算，主要感光元件省電來源是讓 CameraX 真正關閉。
- 為讓短暫間歇掃描及時恢復，熄屏監測使用 **有限時的 CPU 部分喚醒鎖**；它本身也會耗電，因此不是零耗電待機。
- **熄屏最長監測 10 分鐘**，之後關閉相機、結束喚醒鎖；若超過 10 分鐘，必須先正常亮屏，再啟動下一輪。間歇模式需要在掃描期間張掌，最慢可能等待數秒；Android 也可能限制熄屏相機重新開啟，請以實測為準。
- 狀態時間軸僅在本機 SharedPreferences 保存短文字，不儲存照片、影片、臉部特徵，不要求網路權限。通知可隨時停止整個服務。

## Samsung S26 Ultra 實機驗收
1. **停止或移除 WakeProbe 服務**，避免兩個 App 同時占用前鏡頭。覆蓋安裝 v0.2.5。
2. 保持平常的斜角手掌與快速滑動設定，先測亮屏時的五種原始手勢。
3. App 內開啟「螢幕關閉時張掌喚醒」，選擇預設「省電優先」，儲存後重新啟動辨識服務。
4. 切回影片、熄屏，在掃描時持續張掌約 1 秒，等待螢幕亮起並由三星臉部辨識直接回到影片。
5. 等候 2～3 秒，試原本張掌握拳點擊及上下滑動、右滑返回、食指游標。若失敗，返回設定頁使用「重新整理喚醒紀錄」查看是否真正關閉 CameraX、完成解鎖及重新啟動相機。
6. 再測按電源鍵亮屏時，臉部解鎖應繼續正常（CameraX 必須釋放）；如果背景重新綁定受系統阻擋，可停止並從畫面中重新啟動 App。
7. 建議對比省電與連續模式的反應及手機發熱；沒有真機量測前不能宣稱節電百分比。

# AirGestureController 隔空手勢控制器 v0.2.4

本版加入兩個**預設關閉、可分開啟用**的實驗性手勢改善功能：
- **斜角張掌輔助**：當原本的 MediaPipe 張掌分類不穩定時，輔助用手部關節伸展判斷；左、右手使用相同邏輯。
- **快速滑動輔助**：第一張有效張掌影像就記錄起點，容許約 260ms 的短暫分類中斷；仍需有效的張掌終點才會觸發上下滑或右滑返回。

一般模式保留原來的張掌、握拳中央點擊、右滑返回及食指游標停留 3 秒點擊邏輯。手機支架斜角、快速揮掌效果仍需 S26 Ultra 實機驗證，不保證所有角度與速度都能辨識成功。

**升級資訊**：Android package `tw.airgesture.controller`、`versionCode=6`、`versionName=0.2.4`，沿用原正式簽章。新功能需開啟對應選項並重新啟動前鏡頭辨識才能生效。

- 現有 v0.2.3 安裝版本**完全不變**；`versionCode`、簽章與 APK 尚未更新。

## 待編譯的下一版原始碼：快速揮掌輔助（2026-10-14）

使用者實測 v0.2.3：張掌綠燈定位後，快速向下揮動容易沒有觸發；刻意慢速移動反而較穩定。

- 問題原因待實機確認。現有 `GestureDecisionEngine` 需**第二張有效張掌影像才建立滑動起點**，且辨識掉幀時立即清空起點。智慧平衡的手部推論間隔約 100 ms，快速揮掌可能錯過有效移動區間。
- 原始碼已新增**「快速揮掌追蹤（實驗性）」開關，預設關閉**。開啟時由第一張有效張掌影像建立起點，仍須至少第二張有效張掌影像並經過至少 100 ms、方向／距離符合原門檻才能執行滑動。
- 中途短暫辨識失敗容許保留原點約 260 ms；MediaPipe 暫時分類為 `None` 的情況在此模式視為短暫掉幀。**沒有新的有效張掌終點就不能觸發滑動**。辨識中斷過久或切換成高信心其他手勢時會重置，降低誤觸。
- 原有握拳點擊、往右返回、上下滑方向與冷卻時間保留；食指游標與 3 秒點擊邏輯不改。新模式只在使用者主動開啟時生效，可與斜角張掌輔助分開測試。
- 已加入未執行的 `FastSwipeAssistTest.kt` 回歸案例，驗證快速上下滑、暫時掉幀、不連續觸發、握拳點擊及舊模式不受影響。
- **仍是原始碼工作階段：沒有執行 Gradle 或 GitHub Actions 編譯、沒有生成 APK，且仍維持 v0.2.3／versionCode 5**。必須等正式編譯與 Samsung S26 Ultra 實機測試後，才能驗證速度改善。
- 注意：若快速動作整段沒有任何新的有效張掌影像，即使有起點暫存，也無法推斷實際手勢；後續可能需要進一步做動態取樣或關節位置追蹤。先避免為了速度直接提高所有推論頻率造成發熱。
